# Data Dictionary — `simulate/ato_dataset.csv`

Generated by `simulate/generate_dataset.py`, implementing the official
`ATO-001` contract from `identify/contract.json` (owned by Person 1).

## Columns beyond the standard IEEE-CIS transaction/identity fields

| Column | Type | Meaning |
|---|---|---|
| `isFraud` | int | Always `1` for every row in this file — this is a pure synthetic fraud dataset, meant to be concatenated with real data, not used alone. |
| `is_synthetic` | bool | Always `True`. Never mix with real data without this flag visible. |
| `attack_id` | str | Always `"ATO-001"` — matches `identify/attacks.json`. |
| `variant_id` | str | One of `ATO-V1` through `ATO-V5` — see `identify/contract.json` for the exact `simulation_config` each implies. |

## Which raw fields were perturbed, per variant

Driven entirely by `identify/contract.json`'s 6 knobs. See that file for
the exact per-variant boolean/float values. Perturbation mechanics
(this implementation's choices, not the contract's):

| Knob | Field(s) touched | How the value is chosen |
|---|---|---|
| `device_change` | `DeviceInfo`, `DeviceType` | Resampled from the real dataset's own value pool, excluding the account's own known devices |
| `location_change` | `dist1`, `addr1` | `dist1`: resampled from real legit distribution's 90th-99th percentile band. `addr1`: resampled from real pool, excluding account's own known addresses |
| `beneficiary_change` | `ProductCD`, `P_emaildomain` | **Substitute signal — not a literal beneficiary field (IEEE-CIS has none). Needs Person 1 sign-off.** Resampled from real pool, excluding account's own known values |
| `amount_change` (float) | `TransactionAmt` | `account's own avg_amount × (1 + amount_change × 5)` — same multiplier formula as Person 1's reference `apply_ato_variant()`, but grounded in the account's real average rather than a raw copied value |
| `velocity_change` (float) | Produces multiple rows | `n_transactions = max(1, round(velocity_change × 10))`, spaced by a gap calibrated from the real dataset's own fast (5th-percentile) inter-transaction gap, scaled inversely with `velocity_change` |
| `time_change` | `TransactionDT` | Shifted into a 2-4 AM window on the same day — matches Person 1's documented reference exactly, for cross-team consistency |

## Known limitations / open items

1. **`beneficiary_change` has no real field to perturb.** IEEE-CIS is
   card-transaction data, not P2P transfer data. `ProductCD` +
   `P_emaildomain` are used as a documented stand-in. **This needs
   Person 1's sign-off** — it's flagged at runtime (see console output
   when generating) and here, not silently assumed correct.
2. **Knob interaction effect**: `velocity_change` > 0 spaces multiple
   transactions across time, which can incidentally shift some of them
   into a different hour-of-day bucket even when `time_change: false`
   (observed in ATO-V1: `time_deviation` is nonzero despite
   `time_change: false`). This is a real side-effect of combining two
   knobs, not a bug — flagged here so it isn't mistaken for a
   miscalibrated `time_change` implementation.
3. **`new_device_rate` / `new_location_rate` validation metrics exclude
   rows with missing raw data** (`DeviceInfo` is null in ~69% of
   transactions — no matching identity record; `addr1` is null in
   ~24%). Missing data isn't evidence of a new device/location, so it's
   excluded from those specific rate denominators rather than counted
   as a false positive signal.
